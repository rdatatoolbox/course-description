What is the DESCRIPTION file?

It is a structured text file that centralizes project metadata and dependencies, providing a clear overview of what a project is about and what it needs to run.

Metadata
Title, description, authors, license, URL, …

Dependencies
External packages used in the project

  Originally designed for R packages, it can also be used in a research compendium.

Adding a DESCRIPTION file

  • It must be placed at the root of the project

  • Its filename has no file extension

  • Its filename must be written in uppercase

The {usethis} package

To create a DESCRIPTION file in your project, try the use_description() function of the {usethis} package.

usethis::use_description()

Why avoid library()?

Two issues with attaching packages w/ library()

  1. Function origin is unclear
library(foo)


bar()
  • Where does bar() come from?
  • Its package of origin is not explicit in the code
  1. Function name conflicts
library(foo)
library(baz)

bar()
  • What if both packages provide a bar() function?
  • The last attached package masks the other one

library("tidyverse")   
## ── Conflicts ────────────────────────────────────────────────────────── tidyverse_conflicts() ## ──
## ✖ dplyr::filter() masks stats::filter()
## ✖ dplyr::lag()    masks stats::lag()
## ℹ Use the conflicted package to force all conflicts to become errors

Prefer the syntax foo::bar()

Make function calls explicit w/ the Double Colon operator

foo::bar()
baz::bar()

Beneficits

  • Clarity: immediately identifies the package providing the function
  • No ambiguity: avoids conflicts between functions with the same name
  • Maintainability: makes code easier to read, understand and reuse

Recommendation

  Always use the syntax foo::bar() in your code1 and do not use library(foo) anymore.

  1. Except if you call many functions of a package many times (e.g. ggplot2)

Depends

  • Packages attached when your project is loaded
  • Their exported functions become available
  • Use it occasionally!

Imports

  • Packages are loaded but not attached
  • Their functions can be called explicitly using foo::bar()
  • Prefer this field!

Recommendation

  Always list your packages in the Imports field and use the syntax foo::bar() in your code.

From DESCRIPTION to a reproducible workflow

Where are we?

  • We have implemented functions in the R/ directory
  • We have described our project in the DESCRIPTION file
  • We have centralized dependencies in Imports (and occasionally in Depends)

  We can now use R package development tools to manage our project

Install dependencies

pak::local_install_deps()

Load project

devtools::load_all()

Install dependencies

Use the local_install_deps() function of the {pak} package to install all packages listed in the DESCRIPTION file

This:

  1. will read package names from the DESCRIPTION file (Depends & Imports)
  2. will install all missing required packages
  3. will update installed packages (unless upgrade = FALSE)
  4. won’t reinstall already installed packages

Usage

pak::local_install_deps()

  For more information

Recommendation

Don’t use the install.packages() function anymore!

Load project

Use the load_all() function of the {devtools} package to load the project

This:

  1. will load packages listed in the Imports field of the DESCRIPTION file
  2. will load & attach packages listed in the Depends field of the DESCRIPTION file
  3. will “source” all functions in the R/ directory

Usage

devtools::load_all()

  For more information

Recommendation

  • Don’t use the library() function anymore!
  • Don’t use the source() function anymore!

Wrap-up

DO

  • Add a DESCRIPTION file to your project
  • List your packages in this file (Imports)
  • Use the syntax foo::bar()
  • Use pak::install_local_deps() to install required packages
  • Use devtools::load_all() to load the project

DON’T

  • Don’t use install.packages()
  • Don’t use library() (use :: or Depends)
  • Don’t use source() to source functions
